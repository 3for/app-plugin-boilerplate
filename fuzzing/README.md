# Fuzzing on transaction parser

[//]: # (Comment)
[//]: # (This file when in the plugin-boilerplate repository is included in the Ethereum Plugin SDK Github page, keep that in mind when editing it.)

Fuzzing allows us to test how a program behaves when provided with invalid, unexpected, or random data as input.

In the case of `app-plugin-boilerplate` we want to test the code that is responsible for handling the contract data.
The fuzzer needs to implement `int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size)`, which provides an array of random bytes that can be used to simulate a serialized transaction.
If the application crashes, or a [sanitizer](https://github.com/google/sanitizers) detects any kind of access violation, the fuzzing process is stopped, a report regarding the vulnerability is shown, and the input that triggered the bug is written to disk under the name `crash-*`. The vulnerable input file created can be passed as an argument to the fuzzer to triage the issue.

> **Note**: Usually we want to write a separate fuzz target for each functionality.

## Manual usage based on Ledger container

### Preparation

Before being able to use the fuzzing tests, the environment must be prepared with all submodules.
To install them, use the following command in the repository root directory:

```shell
git submodule update --init
```

The fuzzer can run from the docker `ledger-app-builder-legacy`. You can download it from the `ghcr.io` docker repository:

```shell
sudo docker pull ghcr.io/ledgerhq/ledger-app-builder/ledger-app-builder-legacy:latest
```

You can then enter this development environment by executing the following command from the repository root directory:

```shell
sudo docker run --rm -ti --user "$(id -u):$(id -g)" -v "$(realpath .):/app" ghcr.io/ledgerhq/ledger-app-builder/ledger-app-builder-legacy:latest
```

### Compilation

Once in the container, go into the `fuzzing` folder to compile the fuzzer:

```shell
cd fuzzing

# cmake initialization
cmake -DBOLOS_SDK=/opt/nanox-secure-sdk -DCMAKE_C_COMPILER=/usr/bin/clang -Bbuild -H.

# Fuzzer compilation
make -C build
```

By default, the fuzz target prints one lightweight heartbeat every 10,000,000
executions:

```
FUZZ_HEARTBEAT execs=10000000 last_size=764
```

Adjust the interval at configure time if you want more or fewer status lines:

```shell
cmake -DBOLOS_SDK=/opt/nanox-secure-sdk \
      -DCMAKE_C_COMPILER=/usr/bin/clang \
      -DFUZZ_HEARTBEAT_INTERVAL=5000000 \
      -Bbuild -H.
```

Set `-DFUZZ_HEARTBEAT_INTERVAL=0` to disable this target-level heartbeat.

### Seed corpus and dictionary

Hand-crafted seeds (one per selector) and a libFuzzer dictionary are checked
into the repo to accelerate coverage:

- `fuzzing/corpus/seed_*` — six valid inputs covering every selector defined
  in `SELECTORS_LIST` (`transfer`, `swapExactTRXForTokens`, dummy, shielded
  `mint` / `transfer` / `burn`).
- `fuzzing/plugin.dict` — TRON address prefix `0x41`, ticker strings,
  uint256 boundary values, common ABI offsets, and the six selector literals.

Both are generated by `fuzzing/seed_corpus_gen.py`. Re-run it after editing
`SELECTORS_LIST` in `src/plugin.h` or when the `txContent_t` layout in the
TRON plugin SDK changes:

```shell
python3 fuzzing/seed_corpus_gen.py
```

### Run

```shell
./build/fuzz -dict=plugin.dict corpus/
```

The `corpus/` argument is both the seed directory and where libFuzzer writes
any new inputs it discovers; the `seed_*` files are loaded alongside the
auto-generated entries on every run.

A successful start prints:

```
INFO: Loaded N dictionary entries from plugin.dict
INFO: seed corpus: files: ...
```

Common variants:

```shell
# Time-boxed run (5 minutes) — useful for CI smoke checks
./build/fuzz -dict=plugin.dict -max_total_time=300 corpus/

# Parallelize across cores
./build/fuzz -dict=plugin.dict -jobs=4 -workers=4 corpus/

# Replay a previously discovered crash without further fuzzing
./build/fuzz crash-<sha1>

# Regression mode: execute every existing input once with no mutation
./build/fuzz -runs=0 corpus/

# Compact the corpus down to a minimal coverage-preserving set
./build/fuzz -merge=1 corpus_min/ corpus/
```

When a sanitizer reports a finding, libFuzzer writes the offending input to
the current working directory as `crash-*`, `leak-*`, or `oom-*` and also
adds it to `corpus/`. Replay the file with `./build/fuzz <file>` to see the
full sanitizer trace.

## Full usage based on `clusterfuzzlite` container

Exactly the same context as the CI, directly using the `clusterfuzzlite` environment.
This flow mirrors what runs in CI, so use it whenever you want a reproducible
local run (or when you don't want to install the Ledger SDK on your host).

More info: <https://google.github.io/clusterfuzzlite/>

The build script in `.clusterfuzzlite/build.sh` wires up the seed corpus and
dictionary automatically:

- It runs `python3 fuzzing/seed_corpus_gen.py` first so the seeds always
  match the current `SELECTORS_LIST` and the current SDK struct sizes.
- It copies `fuzzing/plugin.dict` to `$OUT/fuzz.dict` — OSS-Fuzz's runner
  auto-adds `-dict=$OUT/fuzz.dict` whenever a file with that name exists.
- It packs `fuzzing/corpus/` into `$OUT/fuzz_seed_corpus.zip` — the runner
  unpacks this into the corpus directory on first run, so hand-crafted seeds
  are always available even on a fresh machine.

### Preparation

The principle is to build the container, and run it to perform the fuzzing.

> **Note**: The container contains a copy of the sources (they are not cloned), which means the `docker build` command must be re-executed after each code modification.

```shell
# Prepare directory tree (only needed the first time)
mkdir -p fuzzing/{corpus,out}

# Container generation — must be re-run after any source change
docker build -t app-plugin-boilerplate --file .clusterfuzzlite/Dockerfile .
```

### Compilation

This step executes `.clusterfuzzlite/build.sh` inside the container, writing
the `fuzz` binary, `fuzz.dict`, and `fuzz_seed_corpus.zip` to `fuzzing/out/`.
The build uses a target-level heartbeat interval of 10,000,000 executions by
default; pass `FUZZ_HEARTBEAT_INTERVAL` to change it or set it to `0` to
disable the extra heartbeat.

```shell
docker run --rm --privileged \
    -e FUZZING_LANGUAGE=c \
    -e FUZZ_HEARTBEAT_INTERVAL=10000000 \
    -v "$(realpath .)/fuzzing/out:/out" \
    -ti app-plugin-boilerplate
```

Verify the build dropped all three artefacts:

```shell
ls fuzzing/out/
# fuzz   fuzz.dict   fuzz_seed_corpus.zip
```

### Run

```shell
docker run --rm --privileged \
    -e FUZZING_ENGINE=libfuzzer \
    -e RUN_FUZZER_MODE=interactive \
    -v "$(realpath .)/fuzzing/corpus:/tmp/fuzz_corpus" \
    -v "$(realpath .)/fuzzing/out:/out" \
    -ti gcr.io/oss-fuzz-base/base-runner run_fuzzer fuzz
```

`run_fuzzer` is the OSS-Fuzz wrapper around libFuzzer. With the artefacts in
`$OUT`, the startup banner should now show both the dictionary and the seed
corpus being loaded:

```
INFO: Loaded N dictionary entries from /out/fuzz.dict
INFO: seed corpus: files: 144 ...
```

Newly discovered inputs and any `crash-*` / `leak-*` / `oom-*` files are
written into `/tmp/fuzz_corpus` (= host `fuzzing/corpus/`), so they persist
across container runs.

### Common variants

Pass libFuzzer flags after the fuzzer name; `run_fuzzer` forwards them:

```shell
# Time-boxed run (5 minutes) — matches the typical CI budget
docker run --rm --privileged \
    -e FUZZING_ENGINE=libfuzzer \
    -e RUN_FUZZER_MODE=batch \
    -v "$(realpath .)/fuzzing/corpus:/tmp/fuzz_corpus" \
    -v "$(realpath .)/fuzzing/out:/out" \
    -ti gcr.io/oss-fuzz-base/base-runner \
    run_fuzzer fuzz -max_total_time=300

# Parallelize across cores
docker run --rm --privileged \
    -e FUZZING_ENGINE=libfuzzer \
    -e RUN_FUZZER_MODE=interactive \
    -v "$(realpath .)/fuzzing/corpus:/tmp/fuzz_corpus" \
    -v "$(realpath .)/fuzzing/out:/out" \
    -ti gcr.io/oss-fuzz-base/base-runner \
    run_fuzzer fuzz -jobs=4 -workers=4

# Replay a discovered crash (place it under fuzzing/corpus/ first)
docker run --rm --privileged \
    -e FUZZING_ENGINE=libfuzzer \
    -v "$(realpath .)/fuzzing/corpus:/tmp/fuzz_corpus" \
    -v "$(realpath .)/fuzzing/out:/out" \
    -ti gcr.io/oss-fuzz-base/base-runner \
    reproduce fuzz /tmp/fuzz_corpus/crash-<sha1>
```

### Updating seeds or dictionary

Edit `fuzzing/seed_corpus_gen.py`, then re-run the **Preparation** +
**Compilation** steps — the rebuilt image will regenerate the seed corpus
and dictionary as part of `build.sh`. No manual `cp` or `zip` needed.
